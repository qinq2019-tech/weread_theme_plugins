## 视觉方向

> 本章只覆盖「三套主题专属内容模块」（Phase 1 / 任务 #1）的视觉方向。
> 摘录管理页的交互与信息架构见下一章；实现见 v0.2 实现任务。三套主题常驻可切换，本章任何内容不得导致其中一套被删减或弱化。

---

### 0. 一句话总原则

**书桌是屋里唯一的一张桌子，专属区是桌子旁边摊开的那页纸。**

所以：书桌有框、有底色、有纸纹、有阴影、最大字号 27px；专属区**没有框**，直接落在页面底色上，最大字号 17px。层级不靠装饰拉开，靠「有没有那个框」和「谁说话更响」拉开。

---

### 1. 设计原则

1. **一个主题只回答一个问题。** `paper` 回答「我说过什么」（句子）、`gallery` 回答「我读过什么」（书）、`pastel` 回答「我花了多少时间」（日子）。三套模块对应 `quotes[]` / `log[]` / `stats{}` 三个互不重叠的数据源，天然不会做成「同一模块换色」。
2. **不加第二张卡片。** 专属区不设边框、不设底色、不设阴影、不铺 grain。页面上唯一带框的东西是书桌——这是「不是仪表盘」最硬的一条物理保证（卡片网格是仪表的形状）。
3. **留白比内容多，且留白要均匀。** 专属区总高控制在 96–260px（依主题），横向留白一律 ≥ 32px，纵向节奏使用固定标尺 `4 / 8 / 12 / 18 / 26 / 34 / 40`。
4. **少量但准确。** 三套模块一次最多呈现：3 句 + 3 本 / 14 个书脊 + 1 张题签 / 35 个点 + 3 行字。所有数字都来自本机存储，宁可少一行也不造一个数。

---

### 2. 三套专属模块

放置位置：**书桌下方，独立一条区域**，不进入书桌内部栅格。

理由（为什么不放进书桌）：
- 书桌已被用户确认「对味」，且是 1.55fr/1fr 的双列结构。塞第 5、6 个模块进去，右列会从 2 块变 4 块、高度失控，等于同时改 3 主题 × 2 明暗 = 6 个已验证过的好版面。
- 专属区需要**整套不同的栅格**（2 列 / 3fr+240px / 160px+1fr），塞进书桌就不可能了。
- 专属区放在书桌下方、占满内容区宽度，切换主题时**这一整条的形状会变**（横向便笺叠 → 一排书脊 → 点阵日历）。「换内容气质」这件事才能被一眼看见，而不是要在同一个网格里找差异。

只挂在首页（`detectPage() === 'home'`）。书架页 `/web/shelf` 尚未登录实测，v0.2 不在那里挂任何新东西。

#### 2.1 `paper` → 摘句墙

**命名**：摘句墙（eyebrow：`私人书房 · 摘句`）
**一句话定位**：把还留在手里的句子，一条一条贴在墙上——按时间，不排序，不评价。
**为什么属于这套主题**：私人书房里最像「自己房间」的物件，是一叠便笺、一张贴满纸的墙。它不需要封面、不需要数字，只要字。而纸色主题的 serif 13.5px/1.75 正是为「读一句别人的话」准备的字号。

**版式**

```
私人书房 · 摘句                                    ← eyebrow 10px
摘句墙                                             ← title 17px
更早留下的句子，按时间从上往下。                    ← sub 11.5px（可省略）

┌─ 左 minmax(0,1fr) ─────────────┐ ┌─ 右 200px ──────┐
│▏流程是弱者才要遵循的规矩。     │ │ ┌──┐┌──┐┌──┐   │
│▏ 长安的荔枝 · 3 天前           │ │ │书││书││书│   │
│▏                              │ │ │书││书││书│   │
│▏我是一个很笨的人，只是…        │ │ └──┘└──┘└──┘   │
│▏ 未署名 · 4 天前               │ │  60×150~196    │
│▏第三个句子…                    │ │                │
└────────────────────────────────┘ └────────────────┘
```

- 栅格：`grid-template-columns: minmax(0,1fr) 200px`，`gap: 36px`。（注意：书桌是 `1.55fr 1fr`，这里左列**更宽**，因为摘句需要一行放得下 18–22 个汉字；与书桌略有不同是刻意的，避免两条区域看起来是同一个模块的复制。）
- 左列 · 便笺叠：3 条（≥1280px）/ 2 条（1000–1279px）/ 2 条（<1000px）。条间 `gap: 18px`。
- 右列 · 纸书签：3 条并排（≥1280px）/ 2 条（1000–1279px）/ <1000px 改为横向 3 条 36px 高的窄条，贴在便笺下方。
- 书签条高度：`flex:1; min-height:150px; max-height:196px`——随左列高度在 150–196 之间伸缩，使两列底部接近齐平。这是本区域唯一需要「对齐」的地方。
- 信息密度：**6 个信息点**（3 句 + 3 本书），是全站最低密度的一块。

**视觉语言**

| 元素 | 规格 |
|---|---|
| 单条便笺 `.rk-slip` | `padding-left:14px`；`border-left:1px solid var(--rk-line)`；**无底色、无圆角** |
| 摘句 `.rk-slip-text` | `var(--rk-font-serif)` / 13.5px / 400 / line-height 1.75 / `var(--rk-ink)`；`-webkit-line-clamp:2`（最多 2 行，超出省略号） |
| 来源 `.rk-slip-meta` | 11px / 400 / `var(--rk-ink-soft)` / `margin-top:6px`；格式 `书名 · 3 天前`；两者都没有时整行不渲染 |
| 书签条 `.rk-bookmark` | 60px 宽 × 150–196px 高；`background:var(--rk-surface)`；`border:1px solid var(--rk-line)`；`border-radius:3px 3px 2px 2px`；顶部 6px 高 `var(--rk-accent-soft)` 色带（书签头）；`box-shadow:var(--rk-shadow-soft)` |
| 书签书名 | `writing-mode:vertical-rl`；`var(--rk-font-serif)` / 10.5px / 400 / `letter-spacing:.04em` / `var(--rk-ink)`；最多 9 字，超出 `…`；`padding: 12px 0 0 0`，水平居中 |
| 书签底部进度 | 书签内部 `position:absolute;bottom:10px;left:12px;right:12px;height:2px`，底 `var(--rk-line)`、值 `var(--rk-accent)`；只有该条 `progress` 可解析时才画 |
| 动效 | 书签 hover：`translateY(-2px)` + 边框变 `var(--rk-accent)`，180ms ease。便笺**无 hover 态**（它是纸，不响应用户） |

竖排书名的风险与兜底：`writing-mode:vertical-rl` 在 Chrome/Edge 的 Shadow DOM 内表现稳定，但混合中英文标点可能旋转异常。兜底规则——若某条书名含 ASCII 字符超过 3 个，该条改为竖排但 `text-orientation:mixed`，并只取前 6 字；仍异常则不显示书名、只显示书签头色带 + 底部进度（保留形态，不保留文字）。**宁可少字，不要歪字。**

#### 2.2 `gallery` → 墙上的书

**命名**：墙上的书（eyebrow：`书架画廊 · 书脊`）
**一句话定位**：远看是一排书脊，近看有一张题签——像看一面墙，而不是看一张表。
**为什么属于这套主题**：画廊的语法是「作品 + 标签」，不是「卡片 + 文字」。这套主题冷白墙、墨绿强调、强对比，最适合用**书的物理形态（书脊、隔板、标签牌）**来说话。同时它是三套里最不像「站点榜单」的一块——站点榜单是 4 列封面卡片，我们是**一排竖立的、宽度参差的、没有文字的色块**。

**版式**

```
书架画廊 · 书脊                                    ← eyebrow 10px
墙上的书                                           ← title 17px

┌─ 左 minmax(0,1fr) ─────────────────┐ ┌─ 右 240px ─────┐
│  ▍▍ ▍  ▍▍▍ ▍ ▍▍  ▍▍▍ ▍ ▍▍  ▍ ▍▍▍   │ │ 最近在读       │
│  ▍▍ ▍  ▍▍▍ ▍ ▍▍  ▍▍▍ ▍ ▍▍  ▍ ▍▍▍   │ │ 长安的荔枝     │
│▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁▁│ │ 马伯庸         │
│  隔板线 1px var(--rk-line)          │ │ ▬▬▬▬▬ 28%      │
└─────────────────────────────────────┘ │ 继续读 →       │
        148px 等高（两列严格对齐）      └────────────────┘
```

- 栅格：`grid-template-columns: minmax(0,1fr) 240px`，`gap: 36px`，两列**严格等高 168px**。
- 左列 · 书脊墙：`display:flex; align-items:flex-end; gap:2px; height:168px; border-bottom:1px solid var(--rk-line)`。
  - **形态规则（这一条决定它像书架还是像柱状图）**：书脊**高度必须近乎一致**（三档 `126 / 132 / 138px`，只差 12px），**宽度必须大幅参差**（三档 `14 / 20 / 28px`，差 2 倍）。等宽 + 高度参差 = 柱状图；不等宽 + 等高 = 书架。这是实地画出来才发现的，不要"为了好看"把高度抖动加大。
  - 间距 `2px`（书要挨着，`3px` 以上就出现"条与条"的分离感）。
  - 书脊数量：≥1280px 最多 14 本、1000–1279px 最多 10 本、<1000px 最多 7 本；不足则右侧留白，**绝不用 `flex:1` 把少量书脊撑满整墙**（3 本书拉成 3 根 300px 宽的柱子会立刻变成图表）。书架隔板线（`border-bottom`）永远画满整列——空着的那一段就是"还能放书的位置"。
  - 档位分配：书名做一次稳定 hash，`hash % 3` 定色、`(hash >> 3) % 3` 定宽、`(hash >> 5) % 3` 定高。同一本书每次刷新形态不变。
  - 书脊文字：`writing-mode:vertical-rl`，10.5px，`var(--rk-ink)`，`letter-spacing:.04em`，**在书脊内垂直居中**（`align-items:center` + `padding:12px 0`），上下各留 12px。
  - 字数上限必须按高度算，否则居中的文字会两头同时被 `overflow:hidden` 切掉（书名会从中间开始显示，比截断更难看）：**可用字数 = `floor((高度 - 24) / 13)`** → 126px 放 7 字、132px 放 8 字、138px 放 8 字，超出加 `…`。
  - 宽度 14px 的书脊**不显示文字**（只保留形态），16px 及以上才显示。
  - 书脊细节：顶部 1px 内高光 `inset 0 1px 0 rgba(255,255,255,.35)`（浅色主题）/ `rgba(255,255,255,.06)`（深色），模拟纸脊受光；**不画书脊纹理线、不画书名框、不画装饰图标**。
- 右列 · 题签：`background:var(--rk-surface)` / `1px solid var(--rk-line)` / `border-radius:10px` / `padding:15px 14px` / `box-shadow:var(--rk-shadow-soft)`；`height:168px`，内容垂直排列。168px 是实测值——148px 装不下 `eyebrow + 书名 2 行 + 作者 + 进度 + 链接`，盒子会被内容撑破、底边与隔板线错开。
- 信息密度：**1 个精确信息点（题签）+ 一面氛围**。书脊只负责传达「多与少、厚与薄」，不承担阅读功能。

**书脊区 hover 与点击**

- 书脊 hover：`translateY(-6px)`，220ms `cubic-bezier(.2,.7,.3,1)`；同时加 `box-shadow:var(--rk-shadow-soft)`，`z-index:2`。整排同时只允许一根升起（`transform` 只在 `:hover` 上，不联动兄弟元素）。
- 点击书脊 = 打开该书 `href`（无 href 则不可点，`cursor:default`，hover 不动）。
- 书脊上方不加 tooltip 气泡。浏览器原生 `title` 属性即可——气泡会破坏「墙」的安静。

**题签内部**

| 元素 | 规格 |
|---|---|
| eyebrow | 10px / 600 / `.18em` / uppercase / `var(--rk-ink-soft)` → 文案「最近在读」 |
| 书名 | `var(--rk-font-serif)` / 15px / 600 / 1.35 / `var(--rk-ink)`；`-webkit-line-clamp:2` |
| 作者 | 11.5px / `var(--rk-ink-soft)`；`margin-top:4px`；无作者则不渲染 |
| 进度条 | `margin-top:auto`（贴底）；`height:3px`；轨道 `var(--rk-line)`，值 `var(--rk-accent)`；右侧同行 11px 数字 |
| 链接 | 11.5px / `var(--rk-ink-soft)`；文案「继续读 →」；hover 变 `var(--rk-accent)` + 下划线 `text-underline-offset:3px` |

题签高度固定 168px，内容按 `eyebrow → 书名(≤2行) → 作者 → (auto) → 进度 → 链接` 排列。若在最小字号下仍溢出（书名 2 行 + 长作者），**优先舍掉作者行**，再舍掉进度百分比数字（保留进度条），**绝不让题签变高**——两列等高是这个模块的专业感所在。

#### 2.3 `pastel` → 读过的日子

**命名**：读过的日子（eyebrow：`轻彩空间 · 日历`）
**一句话定位**：把读过的分钟数还原成 35 个点——亮起来的那些，就是你的日子。
**为什么属于这套主题**：轻彩空间的性格是轻快、圆润、颗粒小。点（11px 圆点，无轴线、无标签、无柱子）是它唯一适合的数据形状——只有「今天亮了一点」。而 `stats{}` 是按天累加的 `{seconds}`，正好能画成日历，不需要任何额外字段。

**版式**

```
轻彩空间 · 日历                                    ← eyebrow 10px
读过的日子                                         ← title 17px

┌─ 168px ─────────────┐ ┌─ minmax(0,1fr) ──────────────┐
│ 一 二 三 四 五 六 日 │ │ 本周   3 小时 12 分           │
│ ○  ●  ●  ○  ○  ●  ● │ │ 连着   4 天                   │
│ ●  ○  ●  ●  ●  ○  ○ │ │ 最早   10 月 12 日            │
│ ●  ●  ●  ●  ○  ●  ● │ │                               │
│ ○  ●  ●  ●  ●  ●  ○ │ │ 今天还没开始。翻开就是开始。  │
│ ●  ●  ●  ○  ⊙      │ │                               │
└─────────────────────┘ └───────────────────────────────┘
 11px 点 / gap 9px       ↑ border-left 1px + padding-left 32px
 ○ = 没读（空心圈，不是浅色实心点）
 ⊙ = 今天（2px accent 外圈，不改填充色）
```

- 栅格：`grid-template-columns: 168px minmax(0,1fr)`，`gap: 0`；右列用 `border-left:1px solid var(--rk-line); padding-left:32px` 做分隔（比再画一个框更轻）。`align-items:center`。
- 左列 · 日历点阵：7 列 × 5 行 = 最近 35 天；列 = 周一→周日，行 = 由远及近，**最后一行只画到昨天/今天**，未来日期**不占位、不画灰点**（画未来会变成排期表，不是日子）。
  - 周标题：`一 二 三 四 五 六 日`，10px / `var(--rk-ink-soft)`，每格居中，`margin-bottom:8px`。
  - 点：**11px 圆**（`border-radius:50%`），`gap:9px`；整块宽度 7×11 + 6×9 = 131px，高度 5×11 + 4×9 = 91px。11px 是实测最优——14px 的点会让整块变成主视觉、压过下面 3 行字。
- 右列 · 轻记：3 行 `label + value`，行高 26px；`label` 10.5px `var(--rk-ink-soft)` 宽 48px，「value」`var(--rk-font-serif)` 13px 600 `var(--rk-ink)`；引导语与其下方小字之间 `margin-top:4px`。
- 信息密度：**35 个点（无文字）+ 3 行字 + 至多 1 行引导语**。

**四阶取值与阈值**

| 档 | 条件 | 呈现 |
|---|---|---|
| 0 档 | `seconds === 0` 或无记录 | **空心圈**：`background:transparent` + `box-shadow:inset 0 0 0 1px var(--rk-line)` |
| 1 档 | 1–14 分钟 | `background:var(--rk-heat-1)` 实心 |
| 2 档 | 15–39 分钟 | `background:var(--rk-heat-2)` 实心 |
| 3 档 | ≥ 40 分钟 | `background:var(--rk-heat-3)` 实心 |

为什么 0 档必须是**空心圈**而不是浅色实心点：实测时 0 档用 `var(--rk-line)` 填充，结果"没读的日子"和"读了 5 分钟的日子"几乎分不出来——空心的洞和实心的点是两种语义，一眼就能分。这一条同时省掉了 `--rk-heat-0` 这个令牌。

- 今天：外圈加 `box-shadow: 0 0 0 2px var(--rk-accent)`（1px 在 11px 的点上几乎看不见），**不改填充色**——今天可能还没读，要能看出是"今天"而不是"今天读了"。
- hover：`transform:scale(1.15)`，120ms；`title` 显示「10 月 28 日 · 23 分钟」。0 档点也可 hover（显示「10 月 28 日 · 没有记录」）。
- 不加图例、不加坐标轴、不加平均线、不加柱状图。目标环已经有一个环了，**全站只能有一个环**。

**轻记三行取值**

- 本周：近 7 天 `stats` 秒数合计 → `RK.formatMinutes()`。
- 连着：从今天往前数，连续 `seconds > 0` 的天数（今天为 0 则从昨天开始数，最多显示 999）。
- 最早：`stats` 里最早一个非零日期 → `M 月 D 日`。
- 三行任一值为 0 / 不存在时**整行不渲染**（不写「本周 0 分钟」）。
- 若三行全部不渲染，右列只保留一句引导语（见 §6.3）。

### 3. 共用骨架与栅格

三套模块共用同一层外壳，保证「同一家族」；内部排布三套完全不同，保证「换内容气质」。

```
<section class="rk-wing" data-rk-wing="paper|gallery|pastel">
  <div class="rk-wing-head">        eyebrow + title (+ sub / more)
  <div class="rk-wing-body">        三套各自的栅格
</section>
```

| 属性 | 规格 |
|---|---|
| 外距 | `margin: calc(var(--rk-desk-gap,26px) + 12px) 0 34px` → 紧凑 32 / 适中 38 / 宽松 44（响应 `density`，但不被撑变形） |
| 内距 | `padding: 0 2px`（只在极窄屏生效，正常为 0） |
| 边框/底色/阴影/纹理 | **全部无**。没有 `border`、没有 `background`、没有 `box-shadow`、不铺 `--rk-desk-grain`。与书桌之间靠 32–44px 留白分隔，**不加 `border-top`**（书桌底边已有一条线，再加一条会形成"两条横线夹一张纸"的拥挤感） |
| head 布局 | `display:flex; align-items:baseline; gap:14px; flex-wrap:wrap`；`title` 在后，`more`（可选）`margin-left:auto` |
| head → body 间距 | `18px` |
| 圆角阶梯 | 书桌 22px ＞ 卡内小块 14px ＞ 题签 10px ＞ 书签头 3px ＞ 封面/书脊 2px ＞ 便笺 0 ＞ 圆点 50% ＞ 按钮 999px。**专属区不使用 14px 以上的圆角**，避免"卡片套卡片" |
| 间距标尺 | `4 / 8 / 12 / 18 / 26 / 34 / 40`，不使用其它数值 |
| 纹理 | 无。纸纹（grain）只属于书桌这张"桌子"，专属区是"摊开的页"，留白本身就是质感 |

### 4. 字体与字号阶梯

### 5. 色板策略

**结论：现有 11 个令牌够覆盖 70%，需要新增 7 个。** 不新增的话，有两处必然做不出来或必然出错：

1. 日历三档实心色没有令牌 → 要么写死 hex（深色主题必然露白），要么用 `color-mix()`（Chrome 111+ 可用，但设置页色卡、静态预览、导出的令牌无法同步，且调试时看不到实际色值）。
2. 书脊三档纸色没有令牌 → 只能用 `surface / accentSoft / line` 三色凑，在 `paper` 下这三色都是米色（`#FFFDF8 / #F0E6D6 / #E4DACB`），几乎分不出来，书脊墙会糊成一整块。

#### 5.1 新增令牌（7 个）

| 令牌 | 用途 | 为什么不能复用现有 |
|---|---|---|
| `--rk-heat-1` | 日历 1 档（1–14 分钟） | `accentSoft` 太平，与 0 档 `line` 区分不出来 |
| `--rk-heat-2` | 日历 2 档（15–39 分钟） | 三阶必须同色相不同明度，只能成套定义 |
| `--rk-heat-3` | 日历 3 档（≥40 分钟） | 与 `accent` 同色相但可微调明度，避免"满格"过响 |
| `--rk-spine-1` | 书脊浅色纸 | 需要有对比的三种纸色，`surface` 太亮 |
| `--rk-spine-2` | 书脊中间色 | 同上 |
| `--rk-spine-3` | 书脊深色纸 | 同上 |
| `--rk-shadow-soft` | 书签 / 封面 / 书脊 / 题签的轻阴影 | `deskShadow` 是 `0 18px 40px`，落在 60px 宽的书签上会糊成一团黑 |

`--rk-desk-grain`、`--rk-desk-bg`、`--rk-desk-shadow` **专属区一律不用**（书桌专属）。

#### 5.2 取值（三套主题 × 明暗两态，共 42 个值，一个都不能漏）

**`--rk-shadow-soft`**

- `src/shared/palette.js`：在**每一套主题的 `light` 和 `dark` 对象里各加 7 个字段**（`heat1/2/3`、`spine1/2/3`、`shadowSoft`），命名与现有 `deskBg` / `deskShadow` 的 camelCase 保持一致。6 个对象（paper.light / paper.dark / gallery.light / gallery.dark / pastel.light / pastel.dark）**逐个检查**。

- `options/` 设置页色卡：`RK_PALETTE.swatch()` 目前返回 `[canvas, surface, accent]`，**不要改**。新增令牌不参与色卡，否则三张小色块会变成十块，失去"一眼看出主题气质"的作用。

### 7. 可关闭性

三套模块各自独立开关，写进现有 `settings.deskModules`（扁平结构，与 `greeting/continue/goal/quote` 同级）：

```js
deskModules: {
  greeting: true, continue: true, goal: true, quote: true,
  wingPaper: true,    // 摘句墙
  wingGallery: true,  // 墙上的书
  wingTime: true      // 读过的日子
}
```

- **默认全部 `true`。** 只有当前主题对应的那一个会渲染，不会出现"一次显示三块"。新用户默认主题是 `paper`，所以第一眼看到的是摘句墙的空态引导——这正好是一次功能发现。
- `deepMerge` 已能补齐老用户缺失字段，不需要迁移脚本。
- 关闭后该区域 **完全不渲染 DOM，且不留 `margin`**（不要渲染一个空 `<section>`，否则书桌下方会多出一段 32–44px 的幽灵留白）。
- 关闭当前主题模块后，下方站点内容上移，**不做任何动画过渡**（页面重排带动画会晃）。
- 设置页呈现建议（与 UX 对齐）：**不要并列 3 个开关**——用户不知道"另外两个"是什么，也不知道为什么要关。只显示一行，文案随当前主题变化：
  - `主题内容 · 摘句墙`
  - `主题内容 · 墙上的书`
  - `主题内容 · 读过的日子`
  切换主题时这一行文案跟着变，开关状态各自保留。

### 8. 动效与质感约束

| 允许 | 时长 / 曲线 | 触发条件 |
|---|---|---|
| 边框色、文字色变化 | 160–180ms `ease` | hover / focus |
| 书签 `translateY(-2px)` | 180ms `ease` | hover |
| 书脊 `translateY(-6px)` + 阴影 | 220ms `cubic-bezier(.2,.7,.3,1)` | hover |
| 日历点 `scale(1.15)` | 120ms `ease` | hover |
| 主题切换时色值变化 | 250ms `ease`（现有 `html` 过渡已覆盖，无需新增） | 换主题 |

| 禁止 | 原因 |
|---|---|
| 入场动画（fade-in-up / 逐个淡入） | 首页已有 4 个模块，进来一波动画会很吵；且 SPA 每次导航都会重放 |
| 交错延迟（stagger delay） | 同上，且 `refresh()` 会重绘，动画会重播 = 闪烁 |
| 无限循环动画（pulse / shimmer 骨架屏） | 与"安静"直接冲突。加载态就是**不渲染**，不是闪烁 |
| 数字滚动（count-up） | 属于仪表盘语言 |
| `transform` 以外的位移（`top/left/margin` 动画） | 触发布局重排，页面会抖 |

`prefers-reduced-motion` 已由现有 `.rk-scope *{transition:none!important;animation:none!important}` 统一处理，新增元素只要都在 `.rk-scope` 内即自动生效——**不要为此再写第二套媒体查询**。

质感三条硬约束：
1. 书脊/封面的"立体感"只用 1px 内高光 + `--rk-shadow-soft`，**不画渐变、不画书脊纹理线、不画书页厚度**。
2. 便笺、日历、书脊区**不铺 grain**。全站唯一有纸纹的是书桌。
3. 深色主题下所有阴影走 `--rk-shadow-soft` 的纯黑低透明，不用彩色阴影。

### 9. 明确不要做的事

1. **不要给专属区加边框 / 底色 / 阴影 / grain。** 页面上只能有一张卡片（书桌）。
2. **不要在专属区出现 17px 以上的字。** 书桌的 27px 问候必须是全站最响的。
3. **不要三套主题共用同一个栅格。** 如果 `gallery` 和 `paper` 都是 `1fr/200px` 双列，那就退化成"换配色"了，直接违背本轮目标。
4. **不要三张以上并排的白色卡片**（卡片网格 = 仪表盘形状）。
5. **不要任何图表**：柱状、折线、环形、堆叠条、进度饼。全站只有一个环（目标环），且只能有一个。
6. **不要 `flex:1` 撑满少量书脊 / 少量日历点。** 数据少就留白，这是"安静"的成本，必须付。
7. **不要 emoji、插画、装饰性图标、贴纸。** 书脊墙不画书脊纹理，日历不画天气。
8. **不要"暂无数据"「空空如也」「快来添加吧」以及任何感叹号。**
9. **不要伪造数字**：不写"推荐值"，不写"平均每天 42 分钟"（除非真算出来），不写"本周目标达成 68%"（除非目标真的设了）。
10. **不要入场动画、不要在 refresh 时重播动画。**
11. **不要为了某套主题的专属模块，去改书桌内部布局。** 书桌已验证，本轮不动。
12. **不要在正文阅读器里放这些东西。** 阅读器只做色温层，专属区只在首页。

### 10. 与其他角色对齐

**给 UX（摘录管理）**：摘句墙的单条便笺（`.rk-slip`：左 1px 线 + serif 13.5px/1.75 + `书名 · 相对时间` 的 meta 行）就是**摘录卡片的只读态**。摘录管理页请沿用同一套视觉锚点，额外操作（编辑 / 删除 / 归档）用 `.rk-slip-actions`：11.5px / `--rk-ink-soft` / 右对齐 / **仅在该条 hover 或 focus-within 时出现**，默认不显示，避免首页与摘录管理页长成两个东西。相对时间规则统一为：`刚刚 / 今天 / 昨天 / N 天前 / N 个月前 / N 年前`。

**给前端**：
- 新增 CSS 全部追加在 `05-ui-css.js` 字符串数组末尾的「主题专属区」分节，**不要改动书桌那一段任何一个值**。
- 三套模块共用 `.rk-wing` 外壳，用 `[data-rk-wing="paper"]` 等属性选择器区分内部栅格（这是 Shadow 内部元素，属性选择器可用；注意宿主元素仍只能用 `:host`）。
- 书脊宽度/高度/颜色档位在 JS 里算好写 inline `width/height`，颜色用 `background: var(--rk-spine-N)`——**不要把 hex 写进 JS**。
- 相对时间、书名 hash、连续天数、日历日期键都是纯函数，放在模块内，不进 `00-core.js`。

**风险点（我判断最可能落不了地的三处）**：
1. **竖排文字**（书签名、书脊名）。`writing-mode:vertical-rl` 在 Shadow DOM 内本身没问题，但站点的 `font-family` 可能在竖排下触发意外的字体回退，导致标点旋转或行高塌陷。**建议前端先在 `preview.html` 里验证再写进扩展**，并保留"只显示色块不显示文字"的降级分支。
2. **`stats` 的日期键是本地时区**（`YYYY-MM-DD` 本地）。日历按本地日期取键，跨时区/跨零点不会有问题，但**"连着 N 天"要小心**：如果用户今天还没读，从今天算会显示 0，看着像"断签"。规则已写明（今天为 0 则从昨天起算），实现时别写反。
3. **`log[]` 是按书去重的最新状态（最多 100 本），不是历史流水**。所以"墙上的书"只能表达"最近在读的 N 本"，**不能做"阅读历史时间线"**。如果后续想要时间线，数据层需要新增字段，那是 v0.3 的事，本轮不要迁就。

**像素验证记录（本章的数字是真画出来量过的，不是估的）**

已用真实令牌（`paper` 浅色态）按上述规格搭了一张一次性静态页并截图核对，实测推翻/修正了三处，都已写回上文：

| 原方案 | 实测问题 | 已改为 |
|---|---|---|
| 书脊 宽 14/18/22 + 高 112/126/140 | 等宽 + 高度大跳变，整排读起来就是**柱状图** | 宽度拉大到 14/20/28，高度收到 126/132/138 |
| 日历 0 档 = `line` 实色点，点 14px | "没读"和"读 5 分钟"分不出；14px 点抢掉整块的注意力 | 0 档改空心圈，点降到 11px / gap 9px |
| 题签 `height:148px` | 内容撑破盒子，底边与隔板线错开 20+px | 两列统一 168px |

另有两处是画出来才发现的细节，已写成硬规则：书脊竖排文字必须**垂直居中 + 按高度算字数**（否则居中后两头同时被 `overflow:hidden` 切掉，书名从中间开始显示）；今天的外圈要 **2px**（1px 在 11px 的圆点上几乎不可见）。

`gallery` / `pastel` 两套的验证只做了 `paper` 的浅色态 + 令牌换算，**深色态与另外两套主题仍需在 `preview.html` 里各截图一次确认**——尤其是 `--rk-spine-*` 在深色下是否还分得出三档。

### 11. 备选方案与理由（供取舍）

- **`pastel` 的「专注计时」为什么被换掉**：一个首页上的番茄钟，要么在用户真的去读书时（页面隐藏）继续计时 → 统计的是非阅读时间；要么与阅读器现有的 30s 心跳重复累加 → 同一分钟被记两次。两个方向都是**造数**，违反"数据全部来自本机、不编造数字"。所以 `pastel` 的第三块改成「读过的日子」，专注的**感觉**由"一个点亮起来"承担，而不是由倒计时承担。如果仍要保留计时，最小可行形态是：只做 15/25/45 分钟的**纯展示倒计时**，不写 `stats`、不显示"已记录"，并在文案上明确"这只是一个计时器"——但我建议不做。
- **`gallery` 的「封面画廊」为什么换成「书脊墙」**：封面图只能靠 `RK.adapter.resolveContinue()` 从**当前页面已渲染的封面节点**里按书名文本匹配。首页只有 24 个封面，用户读过的书大概率不在其中；匹配不到就只能给占位色块——**一排灰色占位方块不是画廊，是加载失败**。书脊墙不依赖任何图片，纯排版即可成立，且与站点下方 4 列封面榜单卡片形成明显区分。
- **专属区要不要参与书桌内部布局**：不参与。理由见 §2 开头（6 个已验证版面 + 三套栅格差异 + 形状变化才能被看见）。

### 0. 一句话总原则

**摘录管理不是一张后台表格，是把墙上的便笺取下来一张、擦掉一个字、再贴回去。**

所以：
- 一条摘录在管理页里读起来，必须和首页摘句墙上那条是**同一个东西**（同一条左细线、同一个 serif 13.5px/1.75、同一行 meta）。
- 这一页唯一新增的东西是**"手上那只手"**（改 / 删 / 导出），不是**另一张卡片**。凡是"表格感"的形状——表头行、斑马纹、每行一条横线、右侧常驻按钮列——一律不要。

### 1. 信息架构

#### 1.1 位置

设置页分区顺序（`⋆` 为新增）：

| # | 卡片 | 性质 |
|---|---|---|
| 1 | 主题 | 调外观 |
| 2 | 外观 | 调外观 |
| 3 | 显示内容 | 调开关 |
| 4 | 每日目标 | 调数值 |
| **5** | **摘录 ⋆** | **管内容** |
| 6 | 我的数据 | 管整份数据（JSON 备份 / 清空） |
| 7 | 边界说明 | 页脚 |

**前 4 张卡片的位置一个都不动，新卡片插在「每日目标」之后、「我的数据」之前。**

理由：
1. **索引不变 = 肌肉记忆不变。** 前 4 张是"回来调一下就走"的卡（换主题、开开关、拖目标），用户可能一周来三次。新卡片插在它们**之后**，这 4 张卡的位置、滚动距离、Tab 顺序全部照旧；如果插在中间，每张常用卡都要往下挪 300–800px（摘录列表可能很长）。
2. **与「我的数据」形成"单条 → 整份"的递进。** 上面这张管一条一条的摘录，下面那张管整份 JSON 备份与清空；用户想到"我的摘录"时，视线落在这一带。分开放在页首页尾会变成两个入口。
3. **「边界说明」必须留在最末。** 它是页脚性质的信任声明，任何内容卡排在它后面都会让"声明"变成"中间插播"。

#### 1.2 标题与文案

| 位置 | 文案 | 说明 |
|---|---|---|
| `<h2>` | `摘录` | 2 字，与「主题」「外观」同节奏。**不叫「我的摘录」**——它紧邻「我的数据」，两个「我的」会被读成两套并行体系，而实际是"内容"与"整份数据"的从属关系 |
| hint（有数据时） | `最近留下的在最前；同一本书的句子会归到一组。` | 一句话交代排序 + 分组两件事，正好是下面两个视图开关的语义。不写操作指引（"悬停可以看到改和删"）——那是把可发现性的债写成文案 |
| 空态句（0 条时，替代 hint） | `还没留下句子。在微信读书页面右下角的圆钮里写一句，它就排在这里。` | 见 §7。一句话指路，不给按钮（本页没有能让人当场写一句的入口，给一个"打开微信读书"的按钮等于把用户赶走） |

### 2. 列表组织

#### 2.1 两个视图：一主一辅

| | 主视图（默认） | 辅视图 |
|---|---|---|
| 名称 | `按书` | `按时间` |
| 分组 | 按 `book` 分组，每组一个组头 | 不分组，一条列表 |
| 排序 | 组内时间倒序；组间按"组内最新一条的时间"倒序 | 全部时间倒序 |
| 控件 | toolbar 左侧一个 `.seg`（复用 `options.css` 现有 `.seg` + `options.js` 现有 `renderSeg()`），两个按钮：`按书` / `按时间` | 同左 |

**两个都给，但一主一辅。** 理由：

- **默认必须是「按书」。** 这是本轮新增能力的全部价值所在：`book` 字段存在的意义就是"按书归档"。如果默认按时间，用户永远看不到分组，等于白加字段。
- **「按时间」不能砍。** 两个真实任务只有它能干好：(a) 找"我上周记的那句"——分组视图里每本书的时间是碎在各组里的，跨书回忆时间线是不可能的；(b) 清理连续录入造成的重复条目——同一天记的几条在时间视图里是挨着的，在分组视图里可能隔了八本书。
- **成本很低。** 两个视图是同一份数据、同一套条目 DOM，只有一个 `groupBy` 函数和一个组头渲染的差别；不新增任何数据、不新增任何状态位（只有一个 `view` 枚举）。

**不做的事**：不做第三个"搜索"视图/搜索框。200 条上限、按书分组 + 时间倒序已经够定位；搜索框要配输入、匹配、无结果态、清空按钮、与导出的"筛选结果"的耦合，成本明显高于收益。等真的有人抱怨找不到再进 v0.3。

#### 2.2 列表项的字段与顺序

```
┌─ .quote-item ──────────────────────────────────────────┐
│▏ 流程是弱者才要遵循的规矩。                    [改] [删] │  ← 正文（serif 13.5/1.75），actions 右对齐
│▏                                                       │
│▏ 长安的荔枝 · 第二章 · 2026-08-11                       │  ← meta（ui 11px / ink-soft）
└────────────────────────────────────────────────────────┘
```

固定三段式，顺序不可变：

| # | 元素 | 规格 | 缺省时 |
|---|---|---|---|
| 1 | 正文 `.quote-slip-text` | `var(--rk-font-serif)` / 13.5px / 400 / line-height 1.75 / `var(--rk-ink)`；左 `border-left:1px solid var(--rk-line)` + `padding-left:14px`（与 §2.1 便笺逐项一致）；最多 8 行 + `…`（见 §7 长摘录） | 不可能为空（空内容不允许保存） |
| 2 | meta `.quote-slip-meta` | `var(--rk-font-ui)` / 11px / 400 / `var(--rk-ink-soft)` / `margin-top:6px`；格式 `书名 · 出处 · 2026-08-11` | 三段全缺时整行不渲染（沿用 §2.1 的"两者都没有时整行不渲染"） |
| 3 | 操作区 `.quote-slip-actions` | 11.5px，右对齐，默认 `opacity:0`；`:hover` / `:focus-within` 时显示（见 §9 与 §2.4） | — |

**meta 的两条硬规则**

1. **日期用绝对日期 `YYYY-MM-DD`，不用相对时间。** 这里刻意与 §10 给首页的"刚刚 / 今天 / 昨天 / N 天前"不同：管理页要对账（哪条是上周三记的）、且要能和导出的 Markdown 逐行对上。相对时间在管理页里会变成"3 天前"和"2026-08-11"两套坐标，用户改完一条再看导出文件会以为少了一天。（若视觉同学坚持同形，唯一可接受的折中是"静态显示相对时间、`title` 属性给绝对日期"，但那会让对账多一步悬停，我不建议。）
2. **分隔符统一为 ` · `（空格点空格）**，与首页 meta「书名 · 3 天前」同一个字符，不出现「—」「/」「｜」。

**为什么不在每条上显示 `id` / 存储大小 / 字数**：这些都是"系统的字段"，不是"我的句子"。字数可以进 `title` 都不必。

#### 2.3 200 条上限必须可见

现在 dock 写入时 `quotes.length > 200` 会静默 `slice` 掉最旧一条（`40-dock.js:243`）。**管理页必须让这个上限成为可见事实**，否则用户删了 5 条、又记了 5 条，会发现"最前面那几条不见了"而认为丢数据。

规格：

| 状态 | `.quote-foot`（列表下方常驻一行，11.5px / `--rk-ink-soft`） |
|---|---|
| `0 < n < 200` | `共 12 条 · 上限 200 条` |
| `n === 200` | `共 200 条，已到上限。再记一句会挤掉最旧的一条。` 且 `data-full="1"`（字色仍 `--rk-ink-soft`，只把"上限"三字用 `--rk-ink`；不加红、不加图标） |

- 这一行**常驻**，不是提示条、不消失。它是"这个数字从哪来、能到多大"的唯一说明。
- 删除后**不弹 toast**（数字自己变就够，弹窗会成为噪音）。
- **可选的一行改动（不阻塞本轮）**：dock 录入到顶时把 toast 从「已收进书桌」改成「已收进书桌 · 已到 200 条上限，最旧的一条被挤掉」。这属于 dock 的文案，不算本规格的交付项，但强烈建议一起做——上限在写入那一刻告知，比事后在管理页翻要早得多。

### 3. 编辑

#### 3.1 就地编辑，不做弹层

三个字段（正文 / 书名 / 出处），正文是 1–3 行的短文本。

- **弹层的成本**：焦点陷阱、Esc 与遮罩点击的两条关闭路径、背景 `aria-hidden`、滚动锁定、`inert` 兼容、移动端软键盘遮挡。这些全为了一个 3 字段的表单，属于用大炮打蚊子。
- **就地编辑保住了"同一个东西"这条锚点**：编辑态就长在那条便笺的位置上，改完收回去还是那一张。弹层会让"这条摘录"和"这张表单"变成两个对象。
- **列表长度可控**：同一时刻只有一条处于编辑态（见 §3.3），其余条目照常可读，用户能看着上下几条来回忆自己当时想说什么。

#### 3.2 触发与退出

| 动作 | 触发 | 结果 |
|---|---|---|
| 进入编辑 | 该条 `改` 按钮（鼠标点击或键盘 Enter/Space，按钮原生行为） | 该条切换到编辑态 |
| 保存 | `保存` 按钮；或 `Ctrl/Cmd + Enter` | 校验通过则写存储、退出编辑态 |
| 取消 | `取消` 按钮；或 `Esc` | 丢弃改动、退出编辑态 |
| 换行 | `Enter`（在正文 textarea 内） | 插入换行。**Enter 永不保存**——正文是多行文本 |
| 失焦 | 点页面其它地方 | **什么都不发生**：不保存、不取消、不关闭。编辑态保留，输入内容保留 |

**为什么失焦既不保存也不取消**：
- 失焦即保存 → 用户点错一下就把半截句子存进去了，且没有"取消"的机会（违反"可逆"）。
- 失焦即取消 → 用户点一下别处看个东西，回来发现自己写的两行字没了（最恶劣的一种数据丢失）。
- 只留显式的两个出口，代价是"用户可能忘了自己在编辑"——这个代价用**视觉**兜住（编辑态有明确的边框 + 主色保存按钮，见 §3.4），而且编辑态下点另一条的 `改` 会自动收尾（见 §3.3）。

#### 3.3 同一时刻只有一条在编辑

点另一条的 `改` 时：

1. 当前这条**内容合法**（`text.trim()` 非空）→ **先自动保存当前这条**，再进入新的一条。
2. 当前这条**内容为空**（用户把正文删光了）→ **不切换**，toast「先写点什么」，焦点留在当前 textarea。

理由：用户去点别的，等于已经放弃"继续改这一条"。自动保存比"丢内容"温和（可逆：再点回去还能改），比"拒绝切换并提示先保存"少一次点击。唯一的例外是空内容——那条保存不了，硬切会丢输入，所以退化成"不让你走"。

#### 3.4 三个字段分别怎么落存储

编辑态字段：

| 字段 | 控件 | 初值 | 保存规则 |
|---|---|---|---|
| 正文 | `<textarea class="quote-edit-text">` | `quote.text` | `trim()` 后非空才允许保存；**只 trim 首尾，不压缩内部换行与空格**（用户可能刻意用换行排版） |
| 书名 | `<input type="text" class="quote-edit-book">` | `displayBook(quote)`（见 §5.3） | `trim()`，可为空（= 归入未署名组）。**不自动加/去书名号** |
| 出处 | `<input type="text" class="quote-edit-source">` | `displaySource(quote)`（见 §5.3） | `trim()`，可为空 |

一次保存 = **一次 `chrome.storage.local.set({'rk:data': ...})`**，不是逐字段写。写下的对象：

```js
{
  id: quote.id,          // 不变
  at: quote.at,          // 不变，保存不改时间
  text: 新正文,
  book: 新书名,          // 即使是空串也写，明确表示"用户确认过没有书名"
  source: 新出处
}
```

**关于老数据（只有 `source` 没有 `book`）**：读取路径（渲染、分组、导出）**一律只读**，不迁移、不写回。只有在该条被用户**主动保存**那一刻，才把 `book` 落成正式字段——因为此刻用户正在看这条、正在确认它的书名，这是逐条确认而非批量迁移。等价性：老记录 `{text, source:'长安的荔枝'}` 不动它，用户进去点保存，得到 `{text, book:'长安的荔枝', source:''}`，内容一字不差（见 §5.3 的 displaySource 规则）。

**不做**：不做"编辑历史"、不做"修改时间"字段（`at` 保持录入时间；用户不该看见"这条 3 天前写的、昨天改过"这种元数据——它会让一句自己的话变成一条系统记录）。

#### 3.5 编辑态与只读态的视觉差异

**只允许这五处变化，别的一律不动**（改多了就变成"两个东西"）：

| 变化 | 只读态 | 编辑态 |
|---|---|---|
| 左竖线 | `1px solid var(--rk-line)` | `1px solid var(--rk-accent)` |
| 正文呈现 | `serif 13.5/1.75` 静态文字，clamp 8 行 | `<textarea>`，同 serif 13.5/1.75，无边框、透明底、`resize:vertical`、`min-height:64px; max-height:320px; overflow:auto`（超长靠内部滚动，不撑爆页面） |
| 新增字段行 | 无 | 书名 / 出处两个 `<input>`：`height:28px`、`border:1px solid var(--rk-line)`、`border-radius:8px`、`padding:0 10px`、`font-size:12.5px`、`background:transparent`；聚焦时 `border-color:var(--rk-accent)` |
| 操作区 | `改` `删`（hover/focus 出现） | 常驻：`保存`（`.btn` 主色）+ `取消`（`.btn.ghost`），右对齐；`改` `删` 隐藏 |
| 底部 meta | 有 | 隐藏（书名已经变成输入框，留着会重复显示） |

- 不加阴影、不加底色块、不加"编辑中"角标。**竖线变主色 + 出现两个按钮，就够了。**
- 编辑态不显示"展开"按钮（全文已在 textarea 里）。

#### 3.6 焦点管理

| 时机 | 焦点落点 | 理由 |
|---|---|---|
| 进入编辑 | 正文 `<textarea>`，光标置于**文本末尾**（`el.focus(); el.setSelectionRange(len, len)`） | 用户通常是"再补一句"或"改个错字"，落在末尾比全选更安全（避免误输入覆盖全文）。同时 `scrollIntoView({block:'nearest'})`，防止编辑框沉到视口外 |
| 取消（Esc / 取消按钮 / 空内容被拒后仍留在编辑态） | 该条的 `改` 按钮 | 用户的下一步大概率是"再看看"或"再试一次"，两个动作的起点都在 `改` 上；且 `:focus-within` 保证 actions 在获得焦点时是显示的（§9），不会焦点落在一个 `opacity:0` 的元素上 |
| 保存成功 | 该条 `.quote-item` 容器（`tabindex="-1"`，程序化聚焦） | 内容变了，用户需要**重读这条**确认结果；回到 `改` 按钮会让读屏只念"改，按钮"，确认不了。同时 toast「已保存」 |
| 保存被拒（正文为空） | 正文 textarea | 错误就在这个框里，光标必须回到能修的地方 |
| 自动保存后切到下一条 | 下一条的正文 textarea | 连续改两条时不用再摸一次鼠标 |

### 4. 删除与撤销

#### 4.1 立即删除 + 单一撤销栈（不用 `window.confirm`）

`window.confirm` 只留给"全量清空"（现有 `clearData()`，一次删掉所有摘录 + 阅读记录 + 时长，不可撤销，那个必须拦）。逐条删除用 confirm 是错的：它把"删一句"的成本抬到和"清空所有数据"一样高，用户删到第 5 条就开始不看提示直接回车——**confirm 的滥用会让真正的危险确认失效**。

| 项 | 规格 |
|---|---|
| 窗口 | **8000ms** |
| 撤销栈 | **单一栈、可累积**：`undo = { entries: [{ item, index }], timer }` |
| 删除 | 立即从 `data.quotes` 移除、**立即写 storage**、立即从列表移除 |
| 撤销条位置 | 列表与 `.quote-foot` 之间，一行，**行内**（不是浮动 toast） |
| 撤销条结构 | 常驻空节点 `<p class="quote-undo" role="status"></p>`，删除时填 `textContent` + 挂一个 `撤销` 按钮 |
| 文案 | 1 条：`已删除 1 条`；N 条：`已删除 3 条`。冒号右侧一个 `撤销` 文字按钮（11.5px / `--rk-accent` / 下划线） |
| 继续删下一条 | **可以，且并入同一个栈**；每次删除都重置 8 秒计时 |
| 撤销 | 按 `index` 升序把条目**插回原位**（不是追加到末尾），写 storage，清空撤销条，toast「已恢复」 |
| 过期 | 计时到点 → 清空 `textContent`（撤销条变空并 `hidden`），栈作废，**不弹任何提示**。删除此时正式定案 |
| 关闭/刷新页面 | 撤销条与栈一起消失，删除已在 storage 生效（定案）。**不做"未确认的删除回滚"**——延迟提交会让"关掉页面 = 数据回滚"变成另一种惊吓 |

**为什么窗口是 8 秒，不是 5 秒也不是 15 秒**：
- 5 秒不够：读屏用户要先听完 `role=status` 播报（"已删除 1 条"），再找到并激活"撤销"，5 秒经常不够，这是无障碍事故。
- 15 秒太久：撤销条一直挂在页面上，用户会以为"这条还没真的删掉"，并且离开页面时不会回头确认；删除动作应该有明确的结束点。
- 8 秒 ≈ 一次"看清 + 反应 + 点"的完整预算，也刚好接近现有 toast 的 1800ms 的 4 倍，不会让两个反馈抢同一段时间。

**为什么删除要立即写 storage 而不是延迟提交**：延迟提交看起来更"优雅"（撤销时不用写回），但它把一条删除的最终状态绑在了一个 8 秒的定时器上——定时器在页面关闭时不一定跑完，于是"storage 里还有、界面上没了"或者反过来。立即写 + 撤销时写回，只有一个状态源。

**焦点**：

| 时机 | 焦点落点 |
|---|---|
| 删除后 | 相邻条目的容器（**优先下一条**，没有下一条则上一条，一条都不剩则跳过、由空态接管），因为被删的那条的按钮已经不存在了 |
| 撤销后 | 恢复回来的条目里 `index` 最小那一条的容器 |
| 撤销条过期 | 焦点不动（节点清空但不清除，不是 `display:none` 的焦点陷阱） |

#### 4.2 批量删除：本轮不做

理由：
1. **需要一整套选择态，成本远超收益。** 复选框（可见性、行高变化）、全选（在哪里、全选的是什么范围——当前组还是全部）、选中文案（`已选 3 条`）、Esc 退出、选区与"导出/撤销"的冲突、删完自动退出选择态……每一个都是新的状态位和新的边界。200 条上限下，逐条删的频次极低。
2. **复选框会破坏锚点。** "每条摘录和首页摘句墙那条便笺是同一个东西"是本章唯一不可让的约束；每行前面多一个方块，一眼就不是便笺了，而是一张表。
3. **"全删"已经有出口。** 「我的数据」里的「清空数据」带 confirm，覆盖了极端情况。

**若以后要做，最小形态**（不展开）：toolbar 右侧「选择」，进入后每条左侧出现勾选框、toolbar 换成 `已选 3 条 · 删除 · 完成`，只做"删除所选"，删除同样走 §4.1 的撤销栈（而不是 confirm）。

### 5. 按书归档

#### 5.1 归一化：只做 `trim()`，绝不做模糊匹配

```js
function normName(v) {
  return typeof v === 'string' ? v.trim() : '';
}
```

- 只用 `String.prototype.trim()`。它同时去掉半角空格、全角空格（U+3000）、换行、制表符，够用。
- **不做**：不做大小写折叠、不做全半角折叠、不折叠书名号（`《长安的荔枝》` 与 `长安的荔枝` 是两个组）、不做编辑距离、不做拼音/简繁归一。
- **明确接受的结果**：`长安的荔枝` / `长安的荔枝 `（尾部空格已被 trim 消掉，同组）/ ` 《长安的荔枝》`（多一对书名号，另一组）/ `长安的荔枝（马伯庸）`（另一组）会被当成不同的书。这是刻意的：模糊匹配的失败模式是"两本不同的书被合并了，而且用户看不出来"，那比"同一本书分成两组"更糟——后者一眼可见、可以逐条改书名修好，前者是静默的数据错误。
- **归一化只在内存里做分组键，不回写 storage**。storage 里的 `book` 原样保留（用户可能在尾部留了空格，我们不替他决定）。

#### 5.2 组头与组内排序

```
┌─ .quote-group-head ────────────────────────────────────┐
│ 长安的荔枝  3 条                        导出这一本      │
└────────────────────────────────────────────────────────┘
  <h3 class="quote-group-title"> + <span class="quote-group-count"> + <button class="quote-group-export">
```

| 项 | 规格 |
|---|---|
| 组头语义 | `<h3>`（不是 `div`）。这一节的全部价值是"按书跳读"，只有标题元素能让读屏用户用标题列表一键列出"我摘过哪几本书" |
| 组头样式 | 书名 `var(--rk-font-serif)` / 13.5px / 600 / `--rk-ink`；条数 11px / 400 / `--rk-ink-soft`，紧跟书名后 `margin-left:8px`；组头与第一条之间 `10px`，与上一组最后一条之间 `26px` |
| 组头装饰 | 无底色、无圆角、无边框、无展开箭头（组永远展开，不做折叠）。**不做折叠**：列表本来就是凭滚动长度换来的可扫性，折叠会引入箭头图标、三角旋转动画、展开状态记忆，全是仪表盘语言 |
| 组内排序 | `at` 降序（新的在上） |
| 组间排序 | 组内最新一条的 `at` 降序（刚摘过的那本排最前） |
| 未署名组 | 书名归一后为空的一组，**固定排在最后**，组头显示 `未署名`（与 §2.1 摘句墙 meta 的 `未署名`、书桌的 `— source` 用词一致） |
| `at` 缺失或非法 | 排在该组最后（不伪造时间、也没法排序）。不影响组间顺序的计算（该组按"组内最新一条合法 `at`"计算，全组无合法 `at` 则该组排最后） |
| 单本导出入口 | 组头右侧 `导出这一本`，11.5px / `--rk-ink-soft`，`:hover` 变 `--rk-accent` 加下划线。未署名组也有（导出这一组） |

#### 5.3 `book` 与 `source` 的借用规则（最容易做错的地方）

老数据把书名存在 `source` 里，新数据 `book` 是书名、`source` 是出处。如果读的时候简单地"两个都显示"，老记录会出现 `长安的荔枝 · 长安的荔枝`（重复），导出的 Markdown 里会出现两行书名。

所以**显示层必须是两个函数，而不是"字段直读"**：

```js
// 书名：有 book 就用 book，没有就借用 source（只读，不回写）
function displayBook(q) {
  return normName(q.book) || normName(q.source);
}

// 出处：只有当 book 存在时，source 才是"出处"；否则它是被借走的书名，不再重复显示
function displaySource(q) {
  return normName(q.book) ? normName(q.source) : '';
}
```

| 记录形态 | `displayBook` | `displaySource` | meta 显示 |
|---|---|---|---|
| `{book:'长安的荔枝', source:'第二章'}` | 长安的荔枝 | 第二章 | `长安的荔枝 · 第二章 · 2026-08-11` |
| `{source:'长安的荔枝'}`（老） | 长安的荔枝 | （空） | `长安的荔枝 · 2026-08-11` |
| `{book:'长安的荔枝'}` | 长安的荔枝 | （空） | `长安的荔枝 · 2026-08-11` |
| `{}`（都没有） | （空） | （空） | 无 meta 行；归「未署名」组 |

- **渲染、分组、导出、`aria-label` 四处都必须走这两个函数**，任何一处直读 `q.book` 或 `q.source` 都会在某一类老数据上出错。
- 这两个函数是纯函数，放在 `options.js` 内部即可，不进 `defaults.js`（`defaults.js` 只放默认值，不放业务逻辑）。

### 6. 导出 Markdown

**与现有的 JSON 备份完全无关。** `exportData()` / `importData()` / `clearData()`（`options.js:235/255/282`）保持不动，那是"整份数据可还原的备份"；Markdown 是"给我一本书能贴进笔记的摘录"，**不可导入、不含设置、不含阅读记录**。

#### 6.1 入口与范围

| 入口 | 位置 | 范围 |
|---|---|---|
| `导出 Markdown`（`.btn.ghost`） | toolbar 右侧（与 `.seg` 同一行，`margin-left:auto`）；列表为空时不渲染 | 全部摘录，按当前视图的分组方式输出 |
| `导出这一本` | 组头右侧 | 该组（同一归一化书名）的摘录 |

**没有"导出当前筛选结果"**——本轮不做搜索，唯一可筛的就是视图，而视图只改分组不改集合，所以两个范围就够。这个决定省掉了一个"导出范围跟随 UI 状态"的隐性耦合（用户切了视图再导出，文件内容悄悄变了，最难查）。

#### 6.2 文件名（确切格式）

| 范围 | 文件名 | 例子 |
|---|---|---|
| 全部 | `weread-quotes-YYYY-MM-DD.md` | `weread-quotes-2026-08-14.md` |
| 单本 | `weread-quotes-YYYY-MM-DD-<书名>.md` | `weread-quotes-2026-08-14-长安的荔枝.md` |

- 日期取**导出当天**的本地日期（与 `exportData()` 用 `toISOString().slice(0,10)` 不同——那个是 UTC，晚上 8 点后导出会差一天；Markdown 导出用本地日期 `RK.todayKey()` 的算法，在 `options.js` 内实现一个 5 行的小函数）。
- `<书名>` 净化：去掉 `\ / : * ? " < > |` 与所有换行/制表符，替换为 `-`；去首尾空格与首尾 `.`；截断到 40 个字符；净化后为空则**省略这一段**（退化成"全部"的文件名）。未署名组导出时书名段用 `未署名`。
- 前缀 `weread-quotes-` 与 JSON 备份的 `weread-studio-` 同族可辨：一个是"给笔记看的"，一个是"给扩展还原的"，文件名前缀不同，用户下载目录里不会混。

#### 6.3 Markdown 的确切格式

**全部导出（按书分组）**：

```md
# 摘录

共 12 条 · 导出于 2026-08-14

## 长安的荔枝

> 流程是弱者才要遵循的规矩。

- 出处：第二章
- 2026-08-11

> 我是一个很笨的人，只是不太愿意承认。

- 2026-08-09

## 长安十二时辰

> 一天之内，把长安走完。

- 2026-08-05

## 未署名

> 没有书名的句子也留下来了。

- 2026-08-02
```

**单本导出（组头入口）**：

```md
# 长安的荔枝

共 3 条 · 导出于 2026-08-14

> 流程是弱者才要遵循的规矩。

- 出处：第二章
- 2026-08-11

> 我是一个很笨的人，只是不太愿意承认。

- 2026-08-09
```

**规则清单（逐条都可判定对错）**：

| # | 规则 |
|---|---|
| 1 | 首行一级标题：全部导出固定 `# 摘录`；单本导出为 `# <书名>`（未署名组为 `# 未署名`） |
| 2 | 第一行之后空一行，然后一行元信息：`共 N 条 · 导出于 YYYY-MM-DD`。**不加句号**（与站内 meta 同一套语气） |
| 3 | 分组标题 `## <书名>`；**全部导出时，如果只有一个组，仍然写 `## <书名>`**（保持格式稳定，用户第二次导出时文件结构不变） |
| 4 | 每条正文用 `>` 引用块，**正文的每一行都加 `> ` 前缀**（用户可能在正文里换行；不加会让后半段掉出引用块）。正文里的空行输出为单独一行 `>`（保持引用块不断裂） |
| 5 | 引用块与上一个块之间空一行，与下面的出处行之间也空一行 |
| 6 | 出处行：仅当 `displaySource(q)` 非空时输出 `- 出处：<出处>` |
| 7 | 日期行：`- YYYY-MM-DD`，由 `at` 转本地日期。**`at` 非法/缺失时整行不输出——绝不补今天的日期** |
| 8 | 出处行与日期行的顺序固定：先出处，后日期。两行都没有，则该条只有一个引用块（不出现空行堆积） |
| 9 | 组内顺序 = 视图顺序（`at` 降序）；组间顺序 = §5.2 的组间规则；`at` 非法的条目在该组末尾 |
| 10 | 只输出真实存在的字段：**不写作者、不写出版社、不写进度、不写 `id`、不写"共 N 字"**。文件名与标题也不补任何推断值 |
| 11 | 文件末尾**不加**"由微信读书 · 书房导出"之类的署名行。这个文件会被贴进用户自己的笔记里，任何署名都是别人屋里的贴纸 |
| 12 | 无 emoji、无感叹号、无分隔横线 `---`（同一引用块内相邻两条靠空行分段，`---` 会让每两条摘录之间出现一条粗横线，读起来像被删除线切断） |
| 13 | 换行符统一 `\n`（不写 `\r\n`）。文件末尾保留一个换行 |

#### 6.4 编码与实现要点

- `new Blob([text], { type: 'text/markdown;charset=utf-8' })`，**不加 BOM**。`\uFEFF` 会粘在第一个 `#` 前面，Obsidian / 多数 Markdown 解析器会把首行标题识别失败——这个坑比"Windows 记事本可能显示乱码"更常见。
- 下载沿用 `exportData()` 的 `createObjectURL + a.click() + setTimeout(revoke, 2000)` 流程，但**另写一个 `downloadText(filename, text, mime)` 函数**，不复用 `exportData()`（避免日后改 JSON 备份时意外改到 Markdown）。
- 文本拼装用 `Array.prototype.join('\n')` 逐行推入数组，**不用模板字符串拼一大坨**（空行、缺省行的分支用 push 更好读、更好测）。

#### 6.5 成功反馈

- 下载触发后 `toast('已导出 Markdown')`。不写条数——文件名里没有、文件里第一行就有；toast 只负责"动作发生了"。
- 单本导出：`toast('已导出「长安的荔枝」')`。
- 列表为空时导出入口**不渲染**（不是 disabled），因此不存在"导出了空文件"的路径。

### 7. 空态与边界

铁律沿用视觉章 §6：**不出现「暂无数据」「空空如也」，不留白盒子，不出现插画，不出现 emoji，不出现感叹号。**

| 情况 | 表现 |
|---|---|
| **0 条摘录** | 卡片内只有两样东西：`<h2>摘录</h2>` 和一句引导（serif 13.5px/1.75、`--rk-ink-soft`、左 `border-left:1px dashed var(--rk-line)` + `padding-left:14px`、高度自适应）：`还没留下句子。在微信读书页面右下角的圆钮里写一句，它就排在这里。`。**不渲染** toolbar / 列表 / `.quote-foot` / 导出按钮。虚线左线是"还能写的位置"，与 §6.1 的空白便笺同一个语言 |
| **1 条** | 正常列表。不做"再记一句会更好"之类的劝导 |
| 删光最后一条 | 变成 0 条空态，**但撤销条保留并显示在空态句下方**（否则用户删掉最后一条后无路可退）。撤销条是 `hidden` 状态独立的节点，与列表渲染解耦 |
| **超长摘录（几千字）** | 只读态 `-webkit-line-clamp:8` + 末尾一个 `展开` 文字按钮（11.5px / `--rk-ink-soft`）；展开后**全文显示、不 clamp**，按钮变 `收起`。展开状态是纯 UI 状态、不落存储、刷新后回到折叠。编辑态 `max-height:320px` 内部滚动，不撑爆页面。**导出永远导出全文**，与折叠态无关 |
| **纯空白 / 只有空格** | 保存被拒（`text.trim()` 为空），toast「先写点什么」（与 dock 现有拒空文案同一句），焦点回 textarea，编辑态不退出。**尾随空格被 trim 掉**，内部换行保留 |
| 书名 / 出处纯空白 | 允许保存，落成空串 → 归「未署名」组 / meta 少一段 |
| `at` 缺失或非法 | meta 只显示书名与出处，不显示日期；排序落到末位；导出不输出日期行。**不补时间** |
| `book` 与 `source` 都有值但相同 | 照 §5.3 显示（`displaySource` 会输出与书名相同的出处 → meta 出现 `长安的荔枝 · 长安的荔枝`）。**不做去重**：那需要猜测"用户是不是写重了"，属于模糊匹配，见 §5.1。用户看到重复会自己去改 |
| `quotes` 元素不是对象 / 缺 `text` | 跳过该条不渲染（防御性 `if (!q || typeof q.text !== 'string') return`），不让一条脏数据毁掉整个列表 |
| 200 条到顶 | §2.3 |

### 8. 功能坞入口

现状：`40-dock.js:253–257` 是 `textarea` 下方一个 `display:flex; justify-content:flex-end` 的容器，里面只有「收进书桌」。

| 项 | 规格 |
|---|---|
| 文案 | `管理摘录`（4 字，与右侧「收进书桌」等长，一行两端对齐不偏沉） |
| 位置 | 该容器**左侧**（容器改 `justify-content:space-between`）。主操作留在右下角——那是视觉与鼠标的"发射位"，不能被碰走 |
| 样式 | 复用现有 `.rk-link`（与 footer 的「更多设置」「恢复原版」同一个类），不新增样式 |
| 行为 | **打开设置页并滚到摘录卡片**，同时把焦点放到卡片 `<h2>`（`tabindex="-1"`） |
| 消息 | `chrome.runtime.sendMessage({ type: 'rk:open-options', hash: 'quotes' })` |
| `background.js` 改动 | `rk:open-options` 分支读 `msg.hash`：有 hash 时 `chrome.tabs.create({ url: chrome.runtime.getURL('src/options/options.html') + '#' + msg.hash, active: true })`；无 hash 时保持现有 `chrome.openOptionsPage()`。**约 4 行，不新增任何权限**（`chrome.tabs.create` 无需权限） |
| 设置页侧 | `load().then(render)` **之后**再判断 `location.hash === '#quotes'` → `card.scrollIntoView({ block: 'start' })` + `h2.focus()`。**必须在渲染之后**：渲染前列表高度是 0，滚动会落在页面上半截 |

**为什么不是"只打开设置页"**：用户点「管理摘录」时脑子里是"我那条句子"，不是"设置"。落在一个 7 张卡片的设置页顶上，等于让人重新找一遍。

### 9. 键盘与无障碍

#### 9.1 语义结构

| 元素 | 标签 | 说明 |
|---|---|---|
| 列表 | `<ul class="quote-list">` + `<li class="quote-item">` | 一组一个 `<ul>`。用真列表而不是 `div` 堆：读屏会播报"列表，12 项"，这是定位数量的唯一途径 |
| 分组 | `<section class="quote-group" aria-labelledby="quote-g-1">` + `<h3 id="quote-g-1" class="quote-group-title">` | `id` 用**序号**（`quote-g-1` / `quote-g-2`），**不要用书名拼 id**——书名里可能有空格、引号、全角标点，拼进 id 只会换来一堆转义 bug |
| 「按时间」视图 | 不分组：一个 `<ul>`，无 `<section>` 包裹 | 视图切换时容器结构变化是可接受的（列表语义仍在）；但**切换后焦点要落在列表上**，不能让焦点随旧 DOM 一起消失 |
| 条目容器 | `<li class="quote-item" tabindex="-1">` | `tabindex="-1"` = 可程序化聚焦、不进 Tab 序列。用于保存/删除/撤销后的焦点落点 |

#### 9.2 操作按钮的命名

列表里会有十几个「改」和「删」，**视觉文本相同、`aria-label` 必须各不相同**：

| 按钮 | 可见文本 | `aria-label` |
|---|---|---|
| 编辑 | `改` | `修改这条摘录：长安的荔枝，2026-08-11` |
| 删除 | `删` | `删除这条摘录：长安的荔枝，2026-08-11` |
| 展开 | `展开` | `展开全文：长安的荔枝，2026-08-11` |
| 组导出 | `导出这一本` | `导出「长安的荔枝」的 3 条摘录` |

`aria-label` 的拼装规则：`displayBook(q) || '未署名'` + `，` + 日期（`at` 合法时）；`at` 非法则省略日期段。**不要**把正文塞进 `aria-label`（十几条长句会让读屏卡住），正文本身就在条目里会被读到。

#### 9.3 编辑框的 `aria`

- **用隐式 `<label>` 包裹，不生成 `id`**：
  ```html
  <label class="quote-edit-field">
    <span class="quote-edit-label">正文</span>
    <textarea class="quote-edit-text"></textarea>
  </label>
  ```
  正文 / 书名 / 出处三组同构。隐式关联免去 `id` 生成与唯一性管理，读屏激活时会播报"正文，多行文本"。
- 编辑态容器 `<div class="quote-edit" role="group" aria-label="修改这条摘录">`，让读屏知道这三组属于同一条。
- 书名 / 出处为**可选字段**：不写 `required`、不加 `aria-required`（它们是可选的事实，标 required 会造一个假的必填）。
- 正文不合法时**不依赖 `aria-invalid`**：只 toast + 聚焦。原因是我们没有字段级错误提示的位置，`aria-invalid` 挂上去却没有可关联的错误文本，对读屏用户是无效信息。

#### 9.4 撤销提示用 `role="status"`

- `<p class="quote-undo" role="status"></p>` —— **节点必须常驻在 DOM 里（初始为空、`hidden`），不能等到删除时才 `createElement` 插进去**。很多读屏/浏览器只监听"已存在的 live region 的内容变化"，后插入的节点经常不播报，这是最典型的 aria-live 落地错误。
- `role="status"` 隐含 `aria-live="polite"` + `aria-atomic="true"`，不再重复写属性。
- 撤销按钮放在 live region **内部**：读屏会读出"已删除 1 条，撤销 按钮"，用户不用先听再去找按钮。
- 不要用现有 `toast()` 承载撤销：`.toast` 是 `pointer-events:none`（`options.css:171`）且 1.8s 就消失，里面放不了可点的按钮。

#### 9.5 Tab 顺序

只读态（每条两个可聚焦元素，actions 由 `:focus-within` 变可见）：

```
[按书] [按时间] → [导出 Markdown] → 第 1 条：改 → 删 → 第 2 条：改 → 删 → … → 组头「导出这一本」按 DOM 顺序 → 撤销按钮（若存在）
```

编辑态（该条替换为五个可聚焦元素）：

```
正文 textarea → 书名 input → 出处 input → 保存 → 取消 → 下一条的 改 → 删
```

要求：
- **不能有正向 Tab 走不到的控件**（actions 默认 `opacity:0` 但**必须始终可聚焦**，靠 `:focus-within` 显示；不要用 `visibility:hidden` / `display:none` 隐藏它——那会让键盘用户彻底够不着）。
- 编辑态展开后，DOM 顺序必须与视觉顺序一致（正文在上、按钮在下），不做 `order` / 绝对定位重排。
- 只读态条目**不支持 Enter 进入编辑**（避免与读屏的浏览/激活语义打架）；编辑只有一个入口：`改` 按钮。

#### 9.6 触屏与无 hover 环境

| 环境 | actions 策略 |
|---|---|
| 有 hover（桌面） | 默认 `opacity:0`；`:hover`、`:focus-within` 时 `opacity:1`，`transition: opacity .16s ease` |
| `@media (hover: none)`（触屏 / 无精确指针） | **常显**（`opacity:1`）。没有 hover 就没有"悬停发现"，藏起来等于功能不存在 |
| `@media (max-width: 620px)`（沿用 `options.css` 现有唯一断点） | 常显 + 组头 `导出这一本` 换到组头第二行（`flex-wrap`），按钮高度加到 32px（触控目标 ≥ 32×32） |

#### 9.7 对比度与焦点

- 所有新文字只用 `--rk-ink` / `--rk-ink-soft` / `--rk-accent` 三个既有令牌，不引入新色 → 对比度与站内其它正文同档（`--rk-ink-soft` 在 `--rk-surface` 上满足 AA）。
- `删` 的 hover 色沿用 `.btn.danger` 已有的 `#a33a2c`（`options.css:158`）。**已知取舍**：深色主题下这个红对比度偏低（与现有 `.btn.danger` 同一状况）。本轮不改，因为改它要动 `.btn.danger`（影响「清空数据」），属于另一件事；`删` 的文字本身已经传达了危险语义，不依赖颜色。
- 焦点环复用全局 `:focus-visible { outline: 2px solid var(--rk-accent); outline-offset: 2px }`（`options.css:175`），不自定义。
- 程序化聚焦的容器（`tabindex="-1"`）不需要焦点环（`:focus-visible` 对程序化聚焦不触发），但**必须保留 `outline` 不被 `outline:none` 抹掉**——有的浏览器在下一 Tab 时会用到。

#### 10.2 状态

```js
var ui = {
  view: 'book',            // 'book' | 'time'   视图（不落存储，刷新回默认）
  editingId: null,         // string | null     当前正在编辑的条目 id，全局唯一
  expanded: {},            // { [id]: true }    哪些长条目已展开（纯 UI，不落存储）

```

只有 `view` 与 `editingId` 会影响 DOM 结构；`expanded` 与 `undo` 只影响局部。

#### 10.3 重绘策略（决定这个功能能不能用的关键）

现有 `render()` 是**全量重绘**（主题卡、外观、开关、数据统计全部重建）。摘录列表**绝对不能**走这条路——编辑中的 textarea 会被整个换掉，输入内容与光标一起消失。

| 函数 | 职责 | 何时调用 |
|---|---|---|
| `renderQuotes()` | 只重建 `#quoteCard` 内部的 `quote-toolbar` / `quote-group*` / `quote-list` / `quote-foot`；不动卡片外的任何东西 | 视图切换、保存、删除、撤销、`storage.onChanged` |
| `renderStats()` | 现有函数，「我的数据」里的条数 | 与 `renderQuotes()` 一起调用（删/改后条数要跟着变） |
| `render()` | 现有全量重绘 | **摘录相关操作一律不调用它** |

**编辑态保护**：`editingId` 非空时，`renderQuotes()` 只重绘"除正在编辑的那一条以外的部分"——实际实现更简单的做法是：编辑期间**完全不重绘列表**（编辑是"这一条被接管了"），只在保存/取消那一刻重绘一次。

**tab 间同步**（10 行，但能挡掉一类真实的数据丢失）：监听 `chrome.storage.onChanged`：

```
area === 'local' && changes['rk:data']
  → 重读 data
  → 若 editingId 为空：renderQuotes() + renderStats()
  → 若 editingId 非空：跳过重绘（不吞用户正在输的内容）
     → 退出编辑态时再检查这一条是否还在 storage 里：
        不在 → toast「这一条已经在别处被删掉了」，放弃保存
        在   → 以 storage 的最新值为基准做 diff，提示「这一条在别处被改过」（可选）
```

#### 10.5 本轮明确不做

- 不做搜索框、不做标签、不做收藏/标星、不做排序自定义（只有两个视图）。
- 不做批量删除与选择态（§4.2）。
- 不做跨设备同步、不发任何请求、不加任何权限（`manifest.json` 的 `permissions` 保持 `["storage"]`）。
- 不改 `exportData()` / `importData()` / `clearData()` 的任何一行（`clearData()` 的 confirm 保留）。
- 不用 `innerHTML` 拼任何用户内容：正文、书名、出处、`aria-label` 一律 `textContent` / `value` / `setAttribute`。`aria-label` 里的书名**必须**走 `setAttribute`（不是字符串拼 HTML）。
- 不在设置页引入 Shadow DOM（本页是扩展自己的页面，直接吃 `options.css`；"新 UI 进 Shadow DOM"只约束注入到 weread 站点的 UI）。
